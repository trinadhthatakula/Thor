## Findings to act on

1. **Odin's blanket consumer keep is the strongest immediate core R8 candidate.** Odin 1.1.0 keeps every class and member under `com.valhalla.superuser.**`. Its AAR has 113 classes / 428,052 raw JVM class bytes, but most of that is not removable: Thor uses persistent and isolated root shells, refresh/probing, shell utilities and RootService. Narrowing must preserve the app-process entry point, reflective constructors and Binder contracts. APK savings require an isolated release comparison.
2. **No large, clearly unused top-level core runtime dependency was found.** Coroutines, serialization, persistence, all privilege providers, Billing and DI each have real reachable uses. The small declaration cleanups below should not be sold as meaningful APK reductions.
3. **WorkManager is now a substantial compatibility dependency rather than the new-job execution engine.** It remains necessary for supported upgrades with persisted jobs and for sweep migration. Retirement is a separate migration/product decision, not safe dependency deletion. It is a credible longer-term way to remove an entire library family.
4. **`room-ktx` is empty and redundant.** Its 2.8.5 AAR contains zero classes. Remove the declaration/catalog entry for clarity if desired; only tiny metadata overhead could disappear. Room runtime now owns the Kotlin APIs.
5. **`:bypass` does not use AndroidX core.** Its direct `core-ktx` dependency can be removed after compiling/linting the module. The app already uses core through its own direct declaration and Odin, so this is module isolation/build hygiene, not an app-size opportunity.
6. **DataStore's native counter appears unused by current single-process stores.** The APK audit bounds the compressed native payload at about 10.7 KiB across ABIs. This is small and should not displace the user's focus. Any exclusion needs release reachability proof and a guard against later multiprocess use.

## Support modules and compilation boundaries

### `:bypass`

`bypass/build.gradle.kts:77–80` declares `implementation(libs.androidx.core.ktx)` and `compileOnly(project(":vm-runtime"))`. The module's three Kotlin files (`Bypass.kt`, `DexFieldLayout.kt`, `Helper.kt`) use Android platform APIs, Java APIs and Kotlin standard APIs; source scan found no AndroidX use, fully qualified or imported. The resolved module runtime graph has 22 artifacts because of core-ktx and Kotlin, including an older standalone coroutines/lifecycle selection; the final app graph resolves one version per coordinate, not multiple copies.

Removing the core-ktx edge improves the module boundary and reduces its standalone dependency graph, but will not remove AndroidX core from Thor. Kotlin stdlib remains a valid runtime requirement for this Kotlin module.

The module itself is essential: `ThorApplication.kt:295–296` initializes the hidden-API bypass; privileged package/settings operations rely on it. It is not superseded merely because the RootService path can access certain framework methods without it. `Bypass.kt:257–289` obtains fields named `artMethod`, `declaringClass`, `artFieldOrMethod`, `methods`, `fields`/`iFields`/`sFields` and sentinel members from `Helper` nested classes. `Bypass.kt:309,331–332` resolves the exact `Helper.InvokeStub.invoke` and constructor signatures. Its consumer keeps for `Helper` and `Helper$*` protect reflection and ART layout, not careless blanket application keeping. Widening/removing or optimizing these requires specialized runtime validation, with little likely benefit.

### `:vm-runtime`

Pure Java compile-time stubs: `dalvik.system.VMRuntime` and `sun.misc.Unsafe`. It has **zero external dependencies** on both resolved compile/runtime classpaths. `:bypass` depends on it as **compileOnly**, so these shadow classes do not ship as an implementation module in Thor. Their methods satisfy compilation for real ART-provided runtime classes; deleting the module breaks compilation, changing it to implementation is incorrect. The Java 21 `--patch-module jdk.unsupported=...` setting addresses host javac's package ownership; it is not shipped runtime weight.

## Consumer R8 rules and runtime-only roots

### Odin: surgical candidate, not a recommendation to delete all keeps

Cached source/artifact directory: `~/.gradle/caches/modules-2/files-2.1/com.trinadhthatakula/odin/1.1.0/`. The AAR's `proguard.txt` contains:

```proguard
-keep,allowobfuscation class * extends com.valhalla.superuser.Shell$Initializer { *; }
-keep class com.valhalla.superuser.** { *; }
-keep class com.valhalla.superuser.ipc.** { *; }
-keep interface com.valhalla.superuser.ipc.** { *; }
```

The package keep subsumes most narrower Odin rules. Adding a permissive keep to Thor **does not override** this: R8 keep constraints combine. A real experiment must replace/filter the published consumer rules in a controlled way, ideally fixing and publishing Odin upstream, rather than adding ineffective application rules or editing the global Gradle cache.

## WorkManager retirement: exact constraints

Current new-job execution has moved to Room-backed foreground services:

- `ThorJobLauncher.startBackup/startRestore` delegates to `DataTaskAcceptance` (`ThorJobLauncher.kt:80–130`).
- `ExportJobLauncherImpl.kt:14–24,42–46` starts new exports in the Room-backed data queue and delegates watching to the combined watcher.
- `RoomPrivilegeSweepDrainRuntime.awaitCutover` calls the legacy cutover before claiming service work (`PrivilegeSweepDrainCoordinator.kt:83–105`).

However, `LegacyDataWorkDrainGate.kt:31–34` explicitly states: **“Remove only after every supported upgrade path has drained its persisted THOR_JOB_CHAIN work.”** Its observation waits until no nonterminal WorkInfo remains. Existing data work must not run concurrently with replacement service work: both can write app data/archive outputs. Cancelled/pruned WorkInfo also cannot be treated as proof of the underlying operation outcome.

The watcher still combines Room task status with legacy WorkInfo, suppresses duplicate submissions using old job tags, and cancels the legacy job if the identifier has no Room task. Old export/backup/restore workers remain `@KoinWorker` definitions for reconstruction. Sweep migration closes legacy admission, awaits cancellation and in-process quiescence, then marks ambiguous pending targets as legacy-unknown with ownership checks; `PrivilegeSweepWorker.kt:17–38` reconstructs a persisted request only to fail it safely rather than replay privileged mutations.

Therefore “enough time has passed since release” cannot alone prove WorkManager removable: users can skip versions and upgrade directly with old databases. Retirement needs an explicit supported-upgrade policy or a safe migration that settles/removes all relevant persisted state and preserves recovery information. Only then remove worker classes/DI registration, WorkInfo watching/cancel adapters, WorkManager initializer/foreground manifest entries, the WorkManager dependency and Koin bridge together. Shared Room/core/lifecycle libraries may remain, so dependency download-size totals overstate the eventual saving.

## Transitive family notes

- **Store Billing:** 9.1.0 directly depends on DataTransport API/runtime/CCT, Play services base/basement/location/tasks. Location pulls places-placereport; DataTransport pulls Firebase *encoding* libraries and javax.inject. These are not Firebase analytics integrations in Thor. Constant-pool inspection finds real Billing references from `com.android.billingclient.api.zzdt` to DataTransport classes, so telemetry/support transport is not safely excluded on import evidence. No Billing class constant-pool reference to location APIs was found in this bounded scan, and the prior APK's package report contains no retained `com.google.android.gms.location` package; this suggests R8 already removes that optional code. Excluding the coordinate could change metadata/resources but is not a demonstrated material APK saving. Do not exclude all GMS based on that observation.
- **Koin:** Stately concurrency, concurrent-collections and strict are implementation support. Kotlin reflection is not resolved. Android wrapper transitive appcompat/fragment dependencies overlap other app UI needs; no safe wholesale removal established.
- **Room/WorkManager:** `com.google.guava:listenablefuture:1.0` is the small interface artifact, not full Guava. Thor's awaited Operation helper directly imports ListenableFuture too. SQLite wrappers use the OS engine. `work-runtime-ktx:2.12.0` is a transitive compatibility artifact, not a second WorkManager instance.
- **DataStore/Coil:** Okio is shared and resolves once to 3.18.1. Removing a DataStore Okio declaration cannot remove it from the app if image loading still needs it. DataStore's shaded protobuf package is its persisted preference format.
- **Annotations:** AndroidX annotation, annotation-experimental, JetBrains annotations and jspecify are shared API/build metadata. Their presence in a runtime resolution report does not imply meaningful retained executable APK code.

## DataStore native counter, bounded candidate

All three Thor stores use `preferencesDataStore`. Cached DataStore 1.2.1 source shows `PreferenceDataStoreFactory.create`, default `FileStorage` with `createSingleProcessCoordinator`, and `SingleProcessCoordinator`. The `System.loadLibrary("datastore_shared_counter")` call is in `SharedCounter.Factory` and is used by `MultiProcessCoordinator`; no multiprocess API use exists in Thor production source. Root/app-process components do not gain a DataStore cross-process dependency just by being separate processes: the settings bridge accesses Android settings, not these preference stores.

This is evidence to inspect final R8 reachability; it is not by itself permission to strip a native library and assume every transitive remains single-process. The separate APK audit estimates only **10.7 KiB** compressed payload across the counter's ABIs. If selected, require final absence of reachable MultiProcess/SharedCounter paths, a test or build-time guard against future usage, and settings/vault persistence checks. User explicitly rejected minor asset/font/license optimizations, so do not repackage this small bound as a major saving.

## Disposition

The coordinator's current candidate removes redundant `room-ktx` and bypass core declarations and applies the approved UI declaration cleanup while retaining extended icons. These core declaration changes have near-zero release gain. **The subsequent isolated Odin optimization-only experiment saved too little compressed payload to adopt**; see [the measured result](README.md). Production keep rules remain unchanged. The only larger core library-family removal identified is **WorkManager compatibility retirement**, which is not safe in the current source/upgrade contract and should be discussed as a separate migration. There is no evidence that Thor accidentally ships Room's compiler, Robolectric, test libraries, full Guava, Kotlin reflection, or the `:vm-runtime` stub module in its release runtime graph.
