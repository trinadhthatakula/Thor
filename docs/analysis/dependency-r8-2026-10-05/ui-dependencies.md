# Thor UI dependency audit — 2026-10-05

Scope: read-only inspection of `chore/dependency-r8-cleanup`, based on `dev` `18162fe050b1360c79de0071eed4c59ddcb49622`. No production edits, Gradle builds, or device actions were performed by this agent. The APK agent independently supplied attributed DEX figures.

## Findings that matter

1. **No wholly unused runtime UI library was demonstrated.** There are useful dependency-declaration cleanups, but the release shrinker already removes unused API implementations.
2. **Retain `material-icons-extended` per the maintainer's final decision.** Every icon Thor currently uses is in core 1.7.8. Replacing extended could remove a large build input, but release R8 already discards unused icons; the measured saving did not justify this change. The initial replacement was reverted.
3. **Replace `biometric-ktx` with `biometric` at the same version.** Only base capability APIs are used. KTX is unneeded, but the base library must stay for security/capability correctness. Again likely tiny or zero release savings.
4. **Remove the redundant direct Accompanist declaration if desired, but retain the transitive library.** Coil directly needs DrawablePainter. A source-only search would incorrectly identify it as dead code.
5. **Lottie is the only relatively self-contained UI replacement candidate.** It serves one 50 dp terminal activity animation. The last FOSS release attributes 123,623 raw DEX bytes and 637 methods to Lottie; those are not compressed APK savings and shared optimized code makes attribution approximate. A same-visual Compose/keyframe replacement could eliminate the engine, but this is implementation work with visual validation, not an unused dependency deletion.
6. **The Coil ImageViewTarget keep is narrower and much smaller than a major opportunity.** Its unconditional upstream keep retains View-target APIs unused by this Compose app. The APK agent attributes only 1,131 raw DEX bytes / 22 methods to ImageViewTarget + GenericViewTarget. The rule protects an upstream R8 bug; overriding it is not justified as a major APK optimization.

## Lottie replacement feasibility and validation

The animation has day/night JSON variants (`res/raw/rearrange.json`, `res/raw-night/rearrange.json`), 48,046 and 48,151 source bytes, 60 fps, frames 13–110, a nested vector-box composition. These source byte counts are **not packaged size**. `AnimateLottieRaw.kt:31–45` deliberately resolves day/night by Thor's **in-app theme**, rather than the phone's system theme. That behavior must survive replacement.

The single call site means a small self-contained Compose Canvas/keyframe implementation of the same rearranging-box motion is feasible. A stock spinner would change the visual; do not silently substitute it as dependency cleanup. A proper port should preserve the 50 dp viewport, crop/alignment, loop timing, day/night colors, activity-only lifetime, and reduced-motion expectations, then delete the unused wrapper/JSON/library declarations together.

Affected workflows are whichever installer/package/backup operations display TermLoggerContent, including long-running logs and success transition. Validate light/dark/system-theme combinations and both busy/success states, cancellation/closing during animation, and a release build on emulator plus physical phone. R8-attributed Lottie DEX 123,623 bytes gives a reason to measure, not proof of a >100 KiB final reduction. AppCompat/Okio survive through other libraries, so their complete sizes cannot be credited to removing Lottie.

## R8/transitive conclusions

- Latest mapping contains no androidx.fragment class entries and only a few androidx.appcompat entries, despite biometric/Lottie bringing those Maven artifacts. This demonstrates existing shrinker effectiveness; replacing biometric capability code simply to drop the entire apparent Fragment dependency would overstate gains and risk startup lockout.
- Asgard's JetBrains Compose Android artifacts are forwarding wrappers: sampled UI, Foundation, Material3 and Runtime Android AARs contain **zero class definitions** and depend on the corresponding AndroidX runtime. They are not a second bundled Compose implementation. Do not propose deleting Asgard to remove duplicate Compose engines.
- There is no blanket app-side `-keep` for Compose, Asgard, Coil, Lottie, icons, or Accompanist. `app/proguard-rules.pro:35` explicitly documents that extension configuration UI runs out of process, so Compose/Asgard/Kotlin can shrink freely. Existing app-side blanket rules protect extension ABI, root-process IPC, and framework callbacks; changing them is outside a UI dependency deletion.
- Coil's consumer rule `-keep class * extends coil3.target.GenericViewTarget { *; }` prevents an R8 vertical-merge bug (upstream issue 524864608). `ImageViewTarget` survives despite no View-based Coil call site. A theoretical conditional/allowshrinking rule must retain the no-optimization behavior for any reachable subclass. Estimated raw attribution is only 1,131 bytes; avoid a fragile upstream-rule override for negligible gain.
- The package/namespace DEX attributions and mapping-entry counts above are diagnostic evidence, not removable-byte totals. Inlining, class merging, string sharing and ZIP compression prevent simple addition. Root-controlled same-toolchain candidate APK builds remain the acceptance measure.

Confirm expected artifacts leave/stay in the graph and require compile/tests/lint. Treat Lottie as a separate measured replacement proposal, with preserved visual behavior and device tests; see [the detailed animation inspection](lottie-replacement.md).
